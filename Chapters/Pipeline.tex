\section*{Pipeline}
The custom pipeline at the centre of this project prepares the Xenium-output for the algorithms in this line-up. It continues by preparing the prediction-output, evaluates the masks and finally visualizes the results. All functions (preparation, segmentation, visualization) can be run separately via their respective scripts. The configuration is performed using \textsc{toml} files. Each section of the file will be explained below with a tandem explanation of what the pipeline does.\\
The main file is hard-coded for the high performance cluster (HPC) of the Berlin Institute of Health (BIH). Running this pipeline on a different HPC or on the a personal machine necessitates adaptation.
\begin{figure*}[ht]
    \centering
    \includegraphics[width=\linewidth]{Images/pipeline_overview_new.pdf}
    \caption{Overview of the XenSegEval pipeline. Each step is forwarded to a node on the HPC4Research@BIH. \textbf{Preprocessing:} The input data is split into multiple sets based on the sections identified by \inlineprogram{XenSegEval.proessing.find\us sections} or the section provided by the user in a JSON file. The coordinates of these ROIs set the boundaries of the smaller datasets --- comprised of imaging data, boundaries (not depicted) and SRT. \textbf{Segmentation:} The datasets are given to the segmentation algorithms. \textbf{Evaluating:} Different benchmarking functions are applied on the predictions. Reference based analysis requires a user-provided ground-truth.}
    \label{fig:pipe}
\end{figure*}
\subsection*{Owner and Tasks}
The configuration file begins with setting the users information and the tasks which should be performed. The owner variable has no importance for the pipeline, it is included to discriminate files. The variable \inlinecode{mail} is used to send \textsc{slurm} updates from the HPC, e.g. start time and fail state. It continues with the section \inlinecode{[tasks]} which lists the main functions of the pipeline. Each function requires the output of the one before. Set a tesk to \inlinecode{false} if it should not be executed.
%  caption={config - tasks}
\begin{lstlisting}[style=customIni]
# TOML for XenSegEval
[owner]
name = "<user-name>"
mail = "<email>@<address>"

[tasks]
preprocess = true
segment = true
evaluate = true
plot = true
\end{lstlisting}
\subsection*{Paths}
The pipeline requires the data-location and output-directory to be set beforehand. \inlinecode{home} defines the location where the directory containing the results will be created. The name of the output-directory is set with \inlinecode{sample\us name}. This directory contains at the end the following
\begin{itemize}
    \item[] \inlinepath{home/sample\us name/processed/}: prepared images, transcript- and boundary-tables;
    \item[] \inlinepath{home/sample\us name/results/\textless method \textgreater/}: predictions and evaluation;
    \item[] \inlinepath{home/sample\us name/run/}: logs and job-files.
\end{itemize}
The \inlinecode{data\us path} variable must link to an unedited, unzipped \textsc{Xenium}-output directory. This requirement is imposed by \textsc{segger}. If \textsc{segger} is excluded, then the content as shown in \figref{dir:XenOut} suffices.\\
If an evaluation with a reference-based method should be performed, then a ground truth must be prepared as a bitmap in \textsc{tif}-format and provided as a path with \inlinecode{gt\us path}. Additionally, the coordinates of the ground-truth must be written in a \textsc{json} file, and linked to in \inlinecode{sections\us path}.\\
% caption={config - paths}
\begin{lstlisting}[style=customIni]
[paths]
# directory the processed data will be saved to
# as default this will be the cloned directory
home = "drive/group/user/home/"
# directory of Xenium-results
data_path = "/.../xenium_output/"
# give a name to the sample
sample_name = "TMA[X]"
# path to ground_truth
gt_path = "/.../ground_truth.tif"
# path to the user-defined section
# one must have the same coordinates
# as the gt-masks
sections_path = "/.../section.json"
\end{lstlisting}
\subsection*{ImageStats}
This section sets the pixelsize of the morphology image and should be reviewed before starting a run on new data. The units are in micrometers and is assumed to be equivalent in x and y directions.
% caption={config - stats}
\begin{lstlisting}[style=customIni]
[ImageStats]
# stats of the morphology.ome.tif
# micrometer per pixel
pixelsize_xy = 0.2125
pixelsize_z = 3.0000
# resolution
y = 64612
x = 51096
\end{lstlisting}
\subsection*{SBATCH}
All tasks are send to HPC-nodes, if the main file is used for execution. The parameters below configure for these nodes.
% caption={config - job}
\begin{lstlisting}[style=customIni]
[sbatch]
# sbatch job specifications
gpu = "gpu:1"
# time in days
time = 2
# RAM in gigabyte
mem = 64
# nr. cores
cpu = 20
\end{lstlisting}
The introduced algorithms, except ProSeg, require a graphics processing unit (GPU) to work efficiently and to render results comparable to those presented in this report. The GPU specification can either be an amount, as shown in the example, or, if a certain model is desired, request for a specific GPU with \inlinecode{gpu:abbreviation:amount}.\\
Some processes, especially ProSeg and image preprocessing, demand more random-access memory (RAM), therefore the requested RAM is doubled.\\ 
The right amount of cores to which subprocesses are distributed, can speed-up the processes, hence many are parallelized using pythons multiprocessing. Currently the most cores are required by the cross evaluation, one core for each output $\approx 20$ cores.\\
Using the function \inlineprogram{XenSegEval.utils.submit\us sbatch} the parameters are collected and written into a job file, retained in \inlinepath{home/sample\us name/run/jobs/}.\\
Below an example bash file for the evaluation of \textsc{DINOCell} which is then send to an HPC node and executed. 
% caption={job file}
\begin{lstlisting}[style=custombash]
#!/bin/bash
#
#SBATCH --job-name=eval_dinocell
#SBATCH --wait
#SBATCH --time=2-00
#SBATCH --mem=64G
#SBATCH --cpus-per-task=20
#SBATCH --output=<home>/<sample_name>/run/logs/eval_dinocell_%N_%j.out
#SBATCH --error=<home>/<sample_name>/run/logs/eval_dinocell_%N_%j.err
#SBATCH --mail-user=philomina-lillie.normann@bih-charite.de
#SBATCH --mail-type=BEGIN,END,FAIL,TIME_LIMIT_90,TIME_LIMIT_80,TIME_LIMIT_50
#
. ~/.bashrc
export PIXI_CACHE_DIR=~/scratch/.cache/pixi
#
pixi run -e eval python -m XenSegEval.eval.eval -c config.toml -m dinocell
\end{lstlisting}
\subsection*{Preprocessing}
The table below contains the parameters to configure the first step in the pipeline, preparing the Xenium-data.\\
If no section, and thus no ground-truth, is defined beforehand, the pipeline uses the lowest resolution of \inlinepath{morphology.ome.tif} to detect the punches in the tissue micro array. \inlinecode{n\us roi} limits the proposed regions, and \inlinecode{buffer} to expand the region. The pipeline then creates an overview image, \inlinepath{home/sample\us name/processed/marked\us regions-of-interest.tif}, as seen in \figref{fig:pipe}.\\
%  caption={config - params}
\begin{lstlisting}[style=customIni]
[preprocessing]
# layers user is interested in
planes = [5, 6, 7]
# number of expected sections
n_roi = 12
# additional space around the roi
# multiplied with width & height
buffer = 0.01
# number of chunks a section is 
# split into for faster processing
# set to zero for None
# must be 0,4,9,16,25,...
chunks = 4
# overlap of chunks
# multiplied with chunk-width/-height
overlap = 0.05
\end{lstlisting}
Using either the detected regions or the coordinates from \inlinepath{sections\us path}, the functions in \inlineprogram{XenSegEval.processing} prepare three folders in \inlinepath{home/sample\us name/processed/}:
\begin{itemize}
    \item[] \inlinepath{boundaries}: tables of the boundary-vertices predicted by {\color{xenium}\textsc{xoa}} for cells and nuclei
    \item[] \inlinepath{morphology}: morphology\us focus images, the DAPI image as multi-layers in OME-TIFF format, and the DAPI image as single-layers in TIFF format.
    \item[] \inlinepath{transcripts} table of transcript location with coordinates in pixel format relative to the section origin
\end{itemize}
The layers kept are set by the \inlinecode{planes} variable --- a list/array containing the indices of the layers in the morphology image --- since not all layers contain comparable amounts of information, as more fluorophores are out of the focus-plane.\\
% the images, morphology and focus, split into the detected (\inlinecode{n\us roi} tells the pipeline how many regions of interest, how many punches, are expected), or provided, punch(es), each ROI in a separate folder, morphology additionally separated into chunks and layers (the layers in all images are defined by the \inlinecode{planes} variable).\\
If the sections are expected to be of significant size, or retain more layers crucial for the segmentation, then the user can provide a number of chunks to split the images. \inlinecode{chunks} must be the integer-root of a quadratic integer. The overlap between the chunks is defined by \inlinecode{overlap}. The example would extend each chunk by 5\% in width and height.\\
\subsection*{Segmentation}
The parameters of the segmentation are configured for each algorithm individually. To adjust which algorithms are applied, exclude their parameters and the table name \inlinecode{[methods.\textless method\textgreater]} from the configuration file. \\
The variables following the table-name are model specific. Consult the documentation of the respective model for a more in-depth explanation of the settings, than is given in the \href{https://github.com/AG-Sawitzki/XenSegEval/blob/main/config.toml}{default configuration file}. Information on model or wrapper definition can be found at the beginning of each parameter-table.\\
\subsection*{Evaluation}
To configure the evaluation, modify the variables under \inlinecode{[evaluation]}
% caption={config - eval}
\begin{lstlisting}[style=customIni]
[evaluation]
# if a evaluation should be performed based on
# Jaccard and related scores
[evaluation.jaccard]
use = false

# Jaccard by deepcell-tools
[evaluation.dc_tools]
use = false

# principal components
[evaluation.pca]
use = false

[evaluation.cross]
use = true
# choose metric
## dc: f1, seg, jaccard, dice, PQ
## u4n: F1, Jaccard
metric = 'F1'
# relevant for 'u4n' metrics
## [0.5,...,1]
threshold = 0.65
# if to include the provided ground truth
include_gt = false
\end{lstlisting}
As discussed in the evaluation, four methods can be applied on the model-predictions. The \inlinecode{use}-variables enable/disable the respective method.\\
For the cross-evaluation the metric and, if the scripts of \inlineprogram{U4N} are used, the threshold, a value between 0.5 and 1, can be specified by the user.\\
\subsection*{Plotting}
Which plots should be generated is adjusted with the variables in \inlinecode{[plotting]}. For further customisation, modify the module \inlineprogram{XenSegEval.plotting}. The user can also set custom colours. The \inlinecode{cmap}-colours may be renamed but not changed in amount. The colours for the algorithms must adhere to the naming convention in \inlinecode{[methods]}, but can be extended upon addition of other algorithms.
\begin{lstlisting}[style=customIni]
[plotting]
cross = false
bars = false
overlay = true

[plotting.colors]
cpsam = '#ffb000'
dinocell = '#fe6100'
dissect = '#dc267f'
mesmer = '#785ef0'
proseg = '#648fff'
segger = '#ba5e3e'
stardist = '#79ab59'
xenium = '#6e006e'

[plotting.cmap]
charite-dunkelblau = '#002552'
charite-blau = '#004d9b'
weiss = '#ffffff'
charite-rapsgeld = '#ffdf43'
charite-mango = '#fab600'
charite-rot = '#e31f2c'
\end{lstlisting}
